# 疫苗及流感藥劑地圖（vaxmap-next）

**語言／Language：** [繁體中文](README.md) ・ [English](README.en.md) ・ 日本語 ・ [한국어](README.ko.md) ・ [Bahasa Indonesia](README.id.md) ・ [Tiếng Việt](README.vi.md) ・ [ไทย](README.th.md) ・ [Filipino](README.tl.md)

本プロジェクトは、台湾衛生福利部疾病管制署（Taiwan CDC）の「疫苗及流感抗病毒藥劑地圖」（vaxmap.cdc.gov.tw）の**概念原型（Proof of Concept）**です。
現行サイトより高速で使いやすいフロントエンド体験を示すことを目的としています。**公式サイトではなく**、いかなる政府ドメインにも公開していません。データは
**リアルタイムのものではなく**、現行サイトから 1 日 2 回取得したスナップショットです（初回スナップショットは 2026-09-21。更新の仕組みは「データの更新方法」と「GitHub Pages へのデプロイ」を参照してください）。本プロジェクトを引き継ぐ場合は、
まず `docs/DATA_SCHEMA.md`（フロントエンドのデータ契約）と `docs/HARVEST.md`（スナップショットの取得方法と制約）に目を通すことをお勧めします。

## 本プロジェクトが何であり、何でないか

- 該当するもの：単一の JSON ファイルを読み込むだけで動作する純粋な静的サイトの原型であり、新しい絞り込み、一覧、地図操作、共有可能な URL の設計を示すものです。
- 該当しないもの：本番稼働のシステム、リアルタイムのデータソース、現行サイトの代替品。距離、在庫、診療時間帯はいずれもスナップショット取得時点のデータです。
  **実際に接種を受ける前に、必ず医療機関へ電話で確認してください**。

## ローカルでの実行

開発サーバーはデフォルトでローカルマシン（127.0.0.1）にのみバインドされます。同じネットワーク内のスマートフォンから接続してテストする場合は、`HOST=0.0.0.0 npm run dev` で起動してください。

要件：Node.js 18 以上（`"type": "module"`。ES modules と `node:test` を使用）。本プロジェクトには**ビルド工程がありません**。
`public/` 配下がそのままデプロイ可能な成果物です。`leaflet`／`leaflet.markercluster` は `devDependencies` にのみ記載されており、
将来 `public/vendor/` 配下のバンドルファイルを再生成する際に使うためのもので、本番稼働時に `npm install` は不要です。
唯一の例外は**データの生成**です。`scripts/normalize.mjs` は `pinyin-pro`（devDependency。ローカル辞書を使い、ネットワーク接続しない）で英語表記を生成するため、
`npm run normalize`／`update-data` を実行する前に `npm install` が必要です（`publish-data.sh` は、パッケージが不足していれば自動的に `npm ci` を実行します）。

```bash
npm run dev        # Start http://localhost:5173/ (override with the PORT environment variable)
```

## テストの実行

```bash
npm test           # Unit tests + data quality tests (node --test)
npm run test:e2e   # Playwright end-to-end smoke tests (desktop 1440x900, mobile 390x844)
npm run test:a11y  # Accessibility checks (reports issues only, never modifies any file)
```

`test:e2e` と `test:a11y` には、環境に `playwright` がグローバルインストールされていること（本プロジェクトはバージョン 1.56 を想定）と、ブラウザーがあらかじめインストールされていること
（`PLAYWRIGHT_BROWSERS_PATH` が Chromium のインストール済みディレクトリを指していること）が必要です。この 2 つのスクリプトは、
`scripts/dev-server.mjs` をランダムな空きポートで自動的に起動し、テスト終了後に自動で停止するため、**サーバーを別途手動で起動する必要はありません**。

## デプロイ

`public/` が公開が必要な唯一のディレクトリです。任意の静的ホスト（Nginx、IIS、S3+CDN、GitHub Pages など）にコピーするだけで動作し、
サーバーサイドのプログラムやデータベースは一切不要です。

### IIS デプロイ時の注意事項

- **MIME タイプ**：`.json` が `application/json` に対応付けられていることを確認してください（IIS ではデフォルトで組み込まれていることが多いですが、ない場合は
  `web.config` に `<staticContent><mimeMap fileExtension=".json" mimeType="application/json" /></staticContent>` を追加します）。
- **静的圧縮**：IIS の Static Compression（`httpCompression`／`urlCompression`）を有効にしてください。
  `hospitals.json` は非圧縮で約 1.9 MB ですが、gzip を有効にすると約 330 KB まで小さくなり、モバイル回線のユーザー体験に大きく影響します。
- **推奨 HTTP ヘッダー**：

  | ヘッダー | 推奨値 | 理由 |
  |---|---|---|
  | `Content-Security-Policy` | `public/index.html` 内の既存の `<meta http-equiv>` 設定をサーバー側に同期する（`frame-ancestors 'none'` は HTTP ヘッダーで設定する必要があり、`<meta>` タグでは `frame-ancestors` を宣言できません） | iframe への埋め込み（クリックジャッキング）を防ぎ、スクリプト／スタイルの読み込み元を制限するため |
  | `X-Content-Type-Options` | `nosniff` | ブラウザーによる MIME タイプの推測に起因するリスクを避けるため |
  | `Referrer-Policy` | `strict-origin-when-cross-origin` | すでに `<meta name="referrer">` で設定済みですが、サーバー側でもう一段追加できます |
  | `X-Frame-Options` | `DENY`（CSP の `frame-ancestors` を使用しない場合） | 上記と同じ目的。古いブラウザー向けの保険的な設定です |

- **キャッシュ方針**：

  | パス | 推奨キャッシュ | 理由 |
  |---|---|---|
  | `data/hospitals.json` | 短いキャッシュ（例：`Cache-Control: no-cache` または `max-age=60~300`） | データは定期的に更新されるため、キャッシュが長すぎるとユーザーに古い在庫が表示されてしまうため |
  | `vendor/**`、`css/**`、`js/**` | 長いキャッシュ＋バージョニング（例：`max-age=31536000, immutable`。ファイル名またはクエリ文字列にバージョン番号を付与） | 内容が変わったときにだけ無効化すればよく、重複ダウンロードを大幅に減らせるため |
  | `index.html` | 短いキャッシュ、またはキャッシュしない | ユーザーが常に最新のリソース参照を取得できるようにするため |

  現在の `scripts/dev-server.mjs`（ローカル開発専用）は、すべてのファイルに `Cache-Control: no-cache` を返します。本番環境では
  上表に従って IIS／CDN 層で別途設定してください。`public/` の内容自体を変更する必要はありません。

## データの更新方法（現在の方法）

`npm run update-data` は次の 3 つを順に実行します。`scripts/harvest.mjs` が現行サイトから全国の医療機関データを取得し、
`data/raw/vaxmap_raw_YYYYMMDD-HHmm.json.gz` として保存します。`scripts/normalize.mjs` が最新の生データを
`public/data/hospitals.json` に変換します（フォーマット契約は `docs/DATA_SCHEMA.md` を参照）。最後にデータ検査を実行します。いずれかのステップが失敗すると処理は中止され、
中途半端なデータが公開されることはありません。取得の詳細と制約は `docs/HARVEST.md` を参照してください。

1 回の完全な取得では、現行サイトに約 280 回のリクエストを送り、100 MB 近くを転送し、10～15 分かかります。ソースデータ自体は医療機関が毎日報告するものであり、
**1 日 1～2 回の更新で十分です。頻度を上げたり、リクエスト間隔を短くしたりしないでください**。現行サイトは海外からの接続を受け付けないため、取得は台湾国内のマシンで実行する必要があります。GitHub Pages と組み合わせた自動更新の方法は次の節を参照してください。

これはあくまで**暫定的な方法**です。本来の方法は、サーバー側から直接データをエクスポートすることです（「推奨する本番のデータ連携方式」を参照）。

## 多言語対応

UI は繁体字中国語（デフォルト）、English、日本語、한국어、Bahasa Indonesia、Tiếng Việt、ไทย、Filipino に対応しており、
ヘッダーの地球儀アイコンのメニューから切り替えられます（ページの再読み込みなし）。言語は、URL の `#lang=en`、前回の選択（localStorage）、
ブラウザーの言語の順に決定され、いずれもなければ繁体字中国語になります。デフォルト以外の言語は共有可能な URL に書き込まれます。県市名は翻訳され、外国語の県市名でも検索できます（例：“Taipei”）。

**医療機関名と住所の英語表記への変換**：`hospitals.json` の各医療機関には、`nameEn`、`addrEn`、`cityEn`、`distEn` が別途含まれます
（`scripts/romanize.mjs` がルールに基づいて生成します。医療用語は用語表を引いて英語に翻訳し、固有名詞は漢語ピンインを使い、県市と行政区は公式の英語名を用い、
住所は郵便局の英語表記の順序に従います。例：「林文正耳鼻喉科診所」→ “Linwenzheng ENT Clinic”、「臺北市北投區明德路92號1樓」→
“1F, No. 92, Mingde Rd., Beitou District, Taipei City”）。言語ファイルの `meta.script` が表示方法を決定します。`latin`（en、ko、id、vi、th、tl）は
英語を主とし、中国語の原文を 2 行目に置きます（タクシー運転手や受付に見せやすくするためです）。`han`（繁体字中国語、日本語）は中国語を主とし、日本語では英語名も併記します。
検索はどの言語でも中国語と英語の両方のフィールドを同時に照合します（“Beitou”、“Mingde”、“ENT”、“Lin Wen Zheng” のいずれでも見つかります）。この変換は機械的なルールで生成されたものであり、
公式の訳名ではないため、一部の名称や住所が完全には正しくない場合があります。

- **文字列の場所**：`public/i18n/<lang>.json`。フラットな key → 文字列の形式で、`zh-Hant.json` が原文です。
- **key の規則**：機能ごとに名前空間を分けます（`filters.today`、`detail.call`、`status.ok.text`）。`{n}` などのパラメーターは必ず保持してください。
  数がちょうど 1 のときは `<key>.one` を使います。HTML は含められません。すべての言語ファイルは、繁体字中国語と完全に同じ key を持つ必要があります（`npm test` が検査します）。
- **言語の追加**：`logic.js` の `SUPPORTED_LANGS` にコードを追加 → `en.json` をコピーして `meta.*` を書き換え、`"_status": "placeholder"` を設定
  → `index.html` の `#lang-select` に選択肢を追加 → `npm test`。詳しい手順と医療用語の対訳は `docs/I18N.md` を参照してください。
- **レビュー状況**（ファイル内の `_status`）：`zh-Hant` は原文、`en` は完了済み。`ja`、`ko`、`id`、`vi`、`th`、`tl` は
  `placeholder`（当面は英語で表示、翻訳待ち）です。

## GitHub Pages へのデプロイ（毎日のデータ自動更新を含む）

**重要な前提：疾病管制署の現行サイトは海外からの接続を受け付けません。** 2026-09-21 の実測では、GitHub Actions の実行マシン（国外にあります）から
`vaxmap.cdc.gov.tw` に接続するとタイムアウトしました（`UND_ERR_CONNECT_TIMEOUT`）。そのため、データ取得を GitHub 上で実行することはできず、
「台湾国内のマシンで取得し、GitHub はデプロイだけを担当する」方式にしています。

```
Linux machine in Taiwan (daily at 05:30, 12:30)  GitHub
  scripts/publish-data.sh                          
    ├─ harvest.mjs harvest → normalize.mjs → data checks  
    ├─ force-push hospitals.json to the data branch  ──►  data branch (always a single commit, so the repo does not grow)
    └─ gh workflow run deploy.yml             ──►  deploy.yml: take the site from main + the newer data from the data branch
                                                    → run sanitizing and checks again → deploy to Pages
```

`.github/workflows/deploy.yml` は、`main` への push、または手動／`publish-data.sh` からのトリガーで実行されます。`data` ブランチの
`hospitals.json` を取り出し、`scripts/keep-live-data.mjs --file` でクレンジングして `main` 内のスナップショットより新しいことを確認できた場合にのみ採用します。`data`
ブランチがない場合は `main` 内のスナップショットをそのまま使います。`.github/workflows/freshness.yml` は毎日 Taipei time (UTC+8) の 09:00 に `data` ブランチのデータを確認し、
36 時間以上更新されていなければその実行を失敗させ、GitHub が repo のオーナーにメールで通知します（取得マシンが動いていないか、失敗し続けていることを意味します）。
サイト画面上の「資料快照」（データのスナップショット）にも「已 N 天未更新」（N 日間未更新）と表示されます。

初回セットアップ：

1. GitHub に公開 repo を作成し、本プロジェクトを push します（デフォルトブランチは `main` である必要があります）。
2. repo の Settings → Pages で Source を **GitHub Actions** に設定し、「デプロイ」ワークフローをもう一度実行します。
3. **台湾国内にあり、現行サイトに接続できる** Linux マシンで（git、Node.js 20 以上、`gh auth login` 済みの GitHub CLI が必要です）、
   プロジェクトフォルダーに移動し、まず手動で一度試します：`npm run publish-data`。成功すれば、10～15 分後にサイト上のスナップショット時刻が更新されます。
4. `scripts/install-updater.sh` を実行して、毎日のスケジュールをインストールします。専用のフォルダーが別途作成され
   （`~/.local/share/vaxmap-updater`。プログラムを修正するフォルダーとは分かれており、実行のたびに自動で `main` を同期します）、
   systemd ユーザータイマーが設定されます。マシンの電源が切れていて実行されなかったスケジュールは、起動後に補完実行されます。削除するには `scripts/install-updater.sh --uninstall` を使用します。

GitHub のセルフホストランナー（self-hosted runner）への切り替えはお勧めしません。**公開** repo では、誰が送った pull request でも
そのマシン上でコードが実行される可能性があり、GitHub 公式もこの使い方を推奨していません。上記の方法では、そのマシンは「外向きに push する」だけで、外部からの指示は一切受け付けません。

GitHub Pages を使う際の注意点：無料プランの Pages には公開 repo が必要です。Pages では HTTP ヘッダーをカスタマイズできないため、
上記の IIS の節で推奨したヘッダーのうち、`index.html` 内の `<meta>` で表現できる部分のみが有効になります（`frame-ancestors` は有効になりません）。
Pages はすべてのファイルを約 10 分間固定でキャッシュするため、データ更新後にユーザーに反映されるまで最大 10 分かかります。

## 推奨する本番のデータ連携方式

現行サイトの `POST /Home/GetHospitalData` API には次の制約があり、フロントエンドから直接呼び出すのには適していません。

- 1 回の呼び出しで返される医療機関データは **20 件**のみで、全件（約 4,660 件）を取得するには約 **280 回**のページング呼び出しが必要です。
- 1 回のレスポンスは約 390 KB で、**サーバー側でレンダリング済みの HTML を含んでいます**（クリーンなデータ形式ではありません）。そのため、全件を取得すると
  転送量は **97 MB** 近くになります。
- `X-Requested-With: XMLHttpRequest` ヘッダーを付けないと受け付けられません。
- **CORS が開放されていない**ため、ブラウザー側からドメインをまたいで直接呼び出すことはできません。

**推奨する方法**：バックエンド（現行サイトが稼働しているサーバー、またはソースデータベースにアクセスする権限のある環境）に**スケジュールジョブ**を作成し、
N 分ごと（例：5～15 分。データの更新頻度に応じて決定）にデータベースから直接エクスポートして、
`docs/DATA_SCHEMA.md` のフォーマットに沿った `hospitals.json` を出力します（正規化後で約 1.9 MB、gzip 圧縮後で約 330 KB。英語表記への変換には `scripts/romanize.mjs` を引き続き利用できます）。
それを静的ファイルホストまたは CDN に公開します。

もう一つの現実的な案は、現行サイトのチームが**全件のデータを返す JSON エンドポイント**を新設することです（ページングの有無は問いませんが、
CORS を開放するか、同一ドメインに配置する必要があります）。効果は上記のスケジュールエクスポートと同等です。

どちらを採用する場合でも、フロントエンドで変更が必要なのは `public/js/data-source.js` の 1 ファイルだけです（`fetch('./data/hospitals.json')` を
新しいエンドポイントの呼び出しに置き換え、返されるオブジェクトが引き続き `{ meta, vaccines, groups, hospitals }` の構造に適合するようにします）。
それ以外のコードを変更する必要は一切ありません。

## セキュリティ

**サードパーティライブラリ**（2026-09-21 に確認）：Leaflet 1.9.4 と leaflet.markercluster 1.5.3 は、どちらも npm 上の最新の安定版です
（Leaflet 2.0 はまだ alpha で、純粋な ESM になりグローバルの `L` が削除されており、markercluster が未対応のため、現時点ではアップグレードを推奨しません）。
`public/vendor/` 内のファイルは npm パッケージとバイト単位で同一であり、`npm run verify-vendor` が sha256 で検証します。`npm test` にもこの検査が含まれています。
`npm audit` の結果は 0 件です。Leaflet には、修正版がまだない報告済みの CVE-2025-69993 があります（`bindPopup()` が渡された文字列を HTML としてレンダリングする件で、
メンテナーはドキュメントに記載された既存の挙動と判断しています）。本サイトは popup／tooltip を**使用しておらず**、すべてのデータ文字列を `textContent` または属性として書き込んでいるため、影響を受けません。

**フロントエンドの防御**：`index.html` の CSP はインラインスクリプトとインラインスタイルを許可せず、画像は 2 つのベースマップドメインのみを許可しています。加えて Trusted Types を有効にしており
（`public/js/trusted-types.js`）、許可するのは Leaflet と `map.js` の固定 HTML 文字列のみです。将来ピンの HTML やベースマップの
著作権表記の文字列を変更する場合は、このファイルの許可リストも同時に更新する必要があります。更新しないと、e2e テストがコンソールエラーで失敗します。外部リンクには必ず `rel="noopener noreferrer"` を付け、
予約用 URL は https のみを受け付けます。ユーザーの位置情報はメモリ上にのみ存在し、URL、ストレージ、いかなるリクエストにも書き込まれません（ただし、地図を拡大すると、ベースマップサーバーはタイルのリクエストからおおよその地域を推測できます）。

**データパイプライン**：ソースサイトのレスポンスは常に信頼できないものとして扱います。`scripts/sanitize.mjs` は、公開するすべてのフィールドをホワイトリスト方式で再構築します
（制御文字と双方向テキスト制御文字の除去、長さの制限、数値範囲と座標範囲のチェック、電話番号と URL の形式チェック）。
`normalize.mjs` と `keep-live-data.mjs` はどちらも、これを最後の関門として使います。`harvest.mjs` には、1 回のレスポンス、総転送量、1 ページあたりの件数、総件数のそれぞれに上限が設けられています。
関連するテストは `tests/security.test.mjs` にあります。

**GitHub Actions**：各ジョブは最小権限とし（`pages: write` を持つのは deploy だけで、repo に書き込めるジョブはありません）、
すべての action は完全な commit SHA に固定し、`${{ }}` は必ず `env:` 経由で渡してコマンドに直接は書き込まず、checkout では認証情報を保持しません。
action のバージョンを上げる際は、あらためて確認して SHA を更新してください。repo の Settings → Environments → github-pages で、`main` ブランチからのデプロイのみが許可されていることを確認することをお勧めします。

**GitHub Pages の制限**：HTTP ヘッダーを設定できないため、`frame-ancestors`／`X-Frame-Options`（他のサイトへの埋め込みを防ぐもの）がありません。
本サイトにはログイン状態や、誘導クリックされ得る機微な操作がないためリスクは低いですが、ヘッダーを設定できるホストにデプロイを切り替える場合は、これらを追加してください。

## ベースマップ

ベースマップは UI の言語に応じて選択され、地名が読めるようになっています（評価の過程と実測の根拠は `docs/BASEMAP.md` を参照）。

- **繁体字中国語**：国土測量製図センター（NLSC）の地図「通用版電子地圖」（汎用版電子地図）`EMAP`（中国語の地名。台湾のユーザーは読み込みが速い）。失敗時は OpenStreetMap の公式タイルに切り替わります。
- **日本語**：繁体字中国語と同じです（日本語ユーザーは漢字の道路名を読め、標識とも一致するため）。
- **その他の言語**（en、ko、id、vi、th、tl）：NLSC の「臺灣通用電子地圖EN」`EMAP8`（台湾全土の英語地名）。失敗時は OpenStreetMap に切り替わり、「地名が中国語で表示される場合があります」と通知します。現在、API キー不要でハングルの道路名を提供するソースがないため、ko も英語を使用します。

**ユーザー自身で切り替え可能**：凡例（デスクトップは左下でデフォルトは展開、モバイルは右上でデフォルトは折りたたみ）内に「底圖」（ベースマップ）のラジオボタンがあります。中国語／日本語の UI では
「通用版電子地圖」「OpenStreetMap」を選べ、外国語の UI では “NLSC (English)”、NLSC の中国語版（地名が標識と一致）、“OpenStreetMap” を選べます。
選択すると即座に地図が切り替わり、著作権表示のバーも一緒に切り替わります。選択内容はブラウザーの localStorage の `vaxmap.basemap` に保存され、**中国語地名系と外国語地名系の 2 種類は別々に記憶され**、
言語を切り替えるとそれぞれが適用されます。選択したベースマップの読み込みに失敗した場合は、これまでどおり自動的に次のものに切り替わって通知が表示され、ラジオボタンも実際に表示されているベースマップのチェックに変わります。

言語を切り替えるとベースマップも即座に切り替わり、ページは再読み込みされません。順序は `public/js/map.js` の `BASEMAP_CHAINS` で決まります（各チェーンの先頭がデフォルトで、
その後ろが順にフォールバックです。同一ホストのレイヤーはまとめて失敗したものと見なされます）。`index.html` の CSP `img-src` はこの 2 つのドメインのみを許可しています（EMAP8 と EMAP は同一ホストです）。テスト時は URL に
`?tiles=nlsc`／`?tiles=osm`／`?tiles=nlscEn` を付けると開始時のベースマップを指定でき（現在の言語のチェーンに含まれている必要があります）、`?tiles=fail` を付けるとデフォルトのベースマップの障害をシミュレートでき、
`?tiles=fail:osm` のような書き方では指定したベースマップだけを失敗させられます。
**正式公開の前に**、必ず次を行ってください。

- [OSM タイル利用ポリシー](https://operations.osmfoundation.org/policies/tiles/)を確認してください。OSM 公式のタイルサーバーは
  寄付で運営されており、可用性は保証されません。ポリシーでは大量のトラフィックを伴う用途でこれに依存してはならないと明記されており、違反すると予告なくブロックされる可能性があります。
  原型や低トラフィックのデモであれば問題ありません。正式な公開サービスのデフォルトのベースマップにする場合は、自前のタイルサーバーか商用のタイルプロバイダー
  （MapTiler、Stadia、Mapbox など。多くは引き続き OSM のデータで地図を作成しています）への切り替えをお勧めします。現在は各言語のデフォルトがすべて NLSC で、OSM はフォールバック時またはユーザーが自分で選択した場合にのみ使われます。
- NLSC の WMTS の公式説明では「使用者無需申請」（ユーザーによる申請は不要）で連携できるとされていますが、公開されているトラフィック上限やサービスレベルはありません。各言語のデフォルトのベースマップはすべて NLSC（EMAP／EMAP8）にあるため、
  正式公開してトラフィックが増える前に、疾病管制署の名義で国土測量製図センターに確認することをお勧めします（`docs/BASEMAP.md` 参照）。

## ブラウザー対応

最新のブラウザー API（`fetch`、ES modules、CSS Grid、`<details>`、`prefers-color-scheme`）を採用しており、
直近 2 年以内の Chrome、Edge、Firefox、Safari（iOS Safari を含む）を対象としています。IE11 には対応せず、そのための polyfill も用意していません。

## 既知の制限

- データはスナップショット（1 日 2 回更新）であり、リアルタイムではありません。接種前に必ず医療機関へ電話で確認してください。
- 診療時間帯は、中央健康保険署（National Health Insurance Administration）のデータから換算したビットマスクで午前／午後／夜間を表しています。あくまで近似的な時間帯であり、正確な外来診療表ではありません。
- 医療機関名と住所はソースの原文を保持しています（例：「台北長庚紀念醫院」は正式名称です）。統一しているのは、県市と行政区のフィールドの「臺」の字だけです。
- 英語の医療機関名は機械的な変換です（人名はピンインを連結し、公式の英語名を使うのは知名度の高い約 25 の病院だけです）。公式の訳名ではありません。
  英語の住所は郵便局のフォーマットで生成され、最初の番地のみを残しています。
- 6 つの外国語（ja、ko、id、vi、th、tl）の UI 文字列は AI による下書きです。正式に公開する前に、ネイティブスピーカーによる校閲を受けてください。
- 位置情報や地図の表示範囲などの状態は、共有可能な URL（URL hash）には書き込まれません。共有されるのは、絞り込み条件と選択した医療機関だけです。
- IE／古い Android WebView では未検証です。ネットワークが不安定な環境では、地図タイルの読み込みに失敗することがあります（自動フォールバックと、手動でのベースマップ切り替えがあります）。

## 現行サイトとの違い

| 現行サイトの問題 | 本原型の対応 |
|---|---|
| サイトに入る際、操作を妨げるお知らせのポップアップを先に閉じる必要がある | お知らせを閉じられるヘッダーのバナー（banner）に変更し、操作を妨げない |
| データが「20 件ごと」の同期 XHR で分割して要求される | 単一の JSON を一度に読み込む（gzip で約 330 KB、英語表記を含む）。絞り込み／並べ替えはフロントエンドのローカルで行う |
| 地図のピンは「診療あり／休診」しか表示しない | ピンは形＋色で、「本日診療あり」と「選択した品目の在庫の有無」の 3 つの状態を同時に表現する |
| 一覧がなく、地図上のピンをクリックするしかない | 距離順に並べた医療機関の一覧を提供し、地図と連動して操作できる |
| 絞り込みは単一選択のポップアップ | 絞り込みを複数選択可能な chips に変更（品目、グループ、地域、在庫ありのみ、本日診療ありなど） |
| 在庫は「あり／なし」のみ表示 | 同じく「在庫あり／なし」のみを表示する（元の数量は、数字の意味を誤解されないよう公開しない） |
| ナビゲーション機能がない | 詳細ページに電話発信（`tel:`）と Google マップのルートリンクを用意 |
| 絞り込み状態を共有できない | 絞り込み条件と選択した医療機関が URL（URL hash）にエンコードされ、そのまま共有、ブックマーク、戻る/進むでの復元ができる |
