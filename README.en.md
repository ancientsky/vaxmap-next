# Vaccine and Influenza Antiviral Map (vaxmap-next)

**語言／Language：** [繁體中文](README.md) ・ English ・ [日本語](README.ja.md) ・ [한국어](README.ko.md) ・ [Bahasa Indonesia](README.id.md) ・ [Tiếng Việt](README.vi.md) ・ [ไทย](README.th.md) ・ [Filipino](README.tl.md)

This is a **concept prototype (Proof of Concept)** of the "Vaccine and Influenza Antiviral Map" (vaxmap.cdc.gov.tw) run by the Ministry of Health and Welfare's Centers for Disease Control (Taiwan CDC),
built to demonstrate a front-end experience that is faster and easier to use than the current site. **This is not an official website**, it is not deployed on any government domain, and its data is
**not live**: it is a snapshot taken from the current site twice a day (first snapshot 2026-09-21; for the update mechanism see "How data is updated" and "Deploying to GitHub Pages"). If you are taking over this project,
start with `docs/DATA_SCHEMA.md` (the front-end data contract) and `docs/HARVEST.md` (where the snapshot comes from and its limitations).

## What this is and is not

- It is: a purely static website prototype that works by reading a single JSON file, demonstrating new filtering, list and map interactions, and a shareable-URL design.
- It is not: a production system, a live data source, or a replacement for the current site. Distances, stock and clinic hours are all as of the snapshot,
  so **always call the facility before going for a vaccination**.

## Running locally

The development server binds to localhost only (127.0.0.1) by default; to test from a phone on the same network, start it with `HOST=0.0.0.0 npm run dev`.

Requirements: Node.js 18 or later (`"type": "module"`, using ES modules and `node:test`). This project has **no build step**:
what is under `public/` is the deployable output as-is. `leaflet` and `leaflet.markercluster` are listed only in `devDependencies`,
for when the bundled files under `public/vendor/` need to be regenerated; they are not needed at runtime, so `npm install` is not required to run the site.
The one exception is **generating data**: `scripts/normalize.mjs` uses `pinyin-pro` (a devDependency with a local dictionary, no network access) to produce the English transliteration,
so run `npm install` before `npm run normalize` / `update-data` (`publish-data.sh` runs `npm ci` automatically if packages are missing).

```bash
npm run dev        # Start http://localhost:5173/ (override with the PORT environment variable)
```

## Running tests

```bash
npm test           # Unit tests + data quality tests (node --test)
npm run test:e2e   # Playwright end-to-end smoke tests (desktop 1440x900, mobile 390x844)
npm run test:a11y  # Accessibility checks (reports issues only, never modifies any file)
```

`test:e2e` and `test:a11y` require `playwright` to be installed globally in the environment (this project assumes version 1.56) and the browsers to be pre-installed
(`PLAYWRIGHT_BROWSERS_PATH` pointing to a directory with Chromium installed). These two scripts start
`scripts/dev-server.mjs` themselves on a random free port and shut it down when the tests finish, so **you do not need to start a server manually**.

## Deployment

`public/` is the only directory that needs to go live. Copy it to any static host (Nginx, IIS, S3+CDN, GitHub Pages, etc.);
no server-side code or database is required.

### IIS deployment notes

- **MIME type**: Make sure `.json` maps to `application/json` (IIS usually has this built in by default; if not, add
  `<staticContent><mimeMap fileExtension=".json" mimeType="application/json" /></staticContent>` to `web.config`).
- **Static compression**: Enable IIS Static Compression (`httpCompression` / `urlCompression`).
  `hospitals.json` is about 1.9 MB uncompressed and drops to about 330 KB with gzip, which matters a great deal for mobile-network users.
- **Recommended HTTP headers**:
  | Header | Recommended value | Reason |
  |---|---|---|
  | `Content-Security-Policy` | Mirror the existing `<meta http-equiv>` settings in `public/index.html` at the server level (`frame-ancestors 'none'` must be set in the HTTP header, since a `<meta>` tag cannot declare `frame-ancestors`) | Prevents embedding in an iframe (clickjacking) and restricts script / style sources |
  | `X-Content-Type-Options` | `nosniff` | Avoids the risks of browsers guessing the MIME type |
  | `Referrer-Policy` | `strict-origin-when-cross-origin` | Already set in `<meta name="referrer">`; the server level can add a second layer |
  | `X-Frame-Options` | `DENY` (if you are not using CSP `frame-ancestors`) | Same as above; a safeguard for older browsers |
- **Caching strategy**:
  | Path | Recommended caching | Reason |
  |---|---|---|
  | `data/hospitals.json` | Short cache (for example `Cache-Control: no-cache` or `max-age=60~300`) | The data is updated periodically, and a long cache would show users out-of-date stock |
  | `vendor/**`, `css/**`, `js/**` | Long cache plus versioning (for example `max-age=31536000, immutable`, with a version number in the file name or query string) | They only need invalidating when content changes, which greatly reduces repeat downloads |
  | `index.html` | Short cache or no cache | Ensures users get the latest resource references |

  Currently `scripts/dev-server.mjs` (for local development only) returns `Cache-Control: no-cache` for every file; in production,
  configure caching separately at the IIS / CDN layer according to the table above. The contents of `public/` do not need to change.

## How data is updated (current approach)

`npm run update-data` does three things in order: `scripts/harvest.mjs` harvests nationwide facility data from the current site and saves it as
`data/raw/vaxmap_raw_YYYYMMDD-HHmm.json.gz`; `scripts/normalize.mjs` converts the latest raw file into
`public/data/hospitals.json` (see `docs/DATA_SCHEMA.md` for the format contract); finally, the data checks run. If any step fails, it aborts
and no half-finished data goes live. For harvest details and limitations, see `docs/HARVEST.md`.

One full harvest sends about 280 requests to the current site, transfers nearly 100 MB, and takes 10–15 minutes. The source data is itself reported daily by the facilities, so
**updating once or twice a day is enough; please do not increase the frequency or reduce the request interval**. The current site does not accept connections from outside Taiwan, so the harvest must run on a machine in Taiwan; for the automated update setup with GitHub Pages, see the next section.

This is still an **interim approach**; the proper approach is a direct server-side data export (see "Recommended production data integration").

## Multilingual support

The UI supports Traditional Chinese (default), English, 日本語, 한국어, Bahasa Indonesia, Tiếng Việt, ไทย and Filipino,
switched from the globe-icon menu in the header (without reloading the page). The locale is taken, in order, from the URL `#lang=en`, the last choice (localStorage), and
the browser language; otherwise it defaults to Traditional Chinese. Non-default locales are written into the shareable URL. County and city names are translated, and you can search using the foreign-language names (for example "Taipei").

**English transliteration of facility names and addresses**: each facility in `hospitals.json` additionally has `nameEn`, `addrEn`, `cityEn` and `distEn`
(generated by rules in `scripts/romanize.mjs`: medical terms are looked up in a glossary and translated into English, proper nouns use Hanyu Pinyin, counties/cities and districts use their official English names,
and addresses follow the Chunghwa Post English ordering, for example 「林文正耳鼻喉科診所」→ "Linwenzheng ENT Clinic", 「臺北市北投區明德路92號1樓」→
"1F, No. 92, Mingde Rd., Beitou District, Taipei City"). The locale file's `meta.script` determines how names are displayed: for `latin` (en, ko, id, vi, th, tl),
English comes first and the original Chinese goes on a second line (handy for showing to a taxi driver or a front desk); for `han` (Traditional Chinese, Japanese), Chinese comes first, and Japanese additionally shows the English name.
In every locale, search matches both Chinese and English fields ("Beitou", "Mingde", "ENT" and "Lin Wen Zheng" are all found). The transliteration is generated by machine rules
and is not an official translation, so a few names or addresses may not be entirely accurate.

- **String location**: `public/i18n/<lang>.json`, a flat key → string map, with `zh-Hant.json` as the source text.
- **Key rules**: keys are namespaced by feature (`filters.today`, `detail.call`, `status.ok.text`); parameters such as `{n}` must be preserved;
  when the count is exactly 1, `<key>.one` is used; HTML is not allowed. Every locale file must have exactly the same keys as Traditional Chinese (`npm test` checks this).
- **Adding a locale**: add the code to `SUPPORTED_LANGS` in `logic.js` → copy `en.json`, edit `meta.*`, and set `"_status": "placeholder"`
  → add an option to `#lang-select` in `index.html` → `npm test`. For detailed steps and the medical terminology glossary, see `docs/I18N.md`.
- **Review status** (`_status` in each file): `zh-Hant` is the source text and `en` is complete; `ja`, `ko`, `id`, `vi`, `th` and `tl` are
  `placeholder` (temporarily shown in English, awaiting translation).

## Deploying to GitHub Pages (with daily automatic data updates)

**Important prerequisite: the Taiwan CDC's current site does not accept connections from outside Taiwan.** In a test on 2026-09-21, connections from the GitHub Actions runners (located abroad) to
`vaxmap.cdc.gov.tw` timed out (`UND_ERR_CONNECT_TIMEOUT`). The data harvest therefore cannot run on GitHub,
so it is done as "harvest on a machine in Taiwan, with GitHub only handling deployment":

```
Linux machine in Taiwan (daily at 05:30, 12:30)  GitHub
  scripts/publish-data.sh                          
    ├─ harvest.mjs harvest → normalize.mjs → data checks  
    ├─ force-push hospitals.json to the data branch  ──►  data branch (always a single commit, so the repo does not grow)
    └─ gh workflow run deploy.yml             ──►  deploy.yml: take the site from main + the newer data from the data branch
                                                    → run sanitizing and checks again → deploy to Pages
```

`.github/workflows/deploy.yml` runs on a push to `main`, or when triggered manually or by `publish-data.sh`: it checks out the `data` branch's
`hospitals.json`, sanitizes it with `scripts/keep-live-data.mjs --file`, and adopts it only after confirming it is newer than the snapshot in `main`; if there is no `data`
branch, it keeps using the snapshot in `main`. `.github/workflows/freshness.yml` checks the `data` branch's data every day at 09:00 Taipei time (UTC+8),
and if it has not been updated for more than 36 hours, it fails that run and GitHub emails the repo owner (meaning the harvest machine is not running or keeps failing);
the "Data snapshot" on the site itself will also show "not updated for N days".

First-time setup:

1. Create a public repo on GitHub and push this project to it (the default branch must be `main`).
2. Go to the repo's Settings → Pages, set Source to **GitHub Actions**, then re-run the "deploy" workflow once.
3. On a Linux machine that is **located in Taiwan and can reach the current site** (it needs git, Node.js 20 or later, and the GitHub CLI with `gh auth login` already done),
   go to the project folder and try it manually once: `npm run publish-data`. If it succeeds, the snapshot time on the site will update after 10–15 minutes.
4. Run `scripts/install-updater.sh` to install the daily schedule. It creates a separate dedicated folder
   (`~/.local/share/vaxmap-updater`, kept apart from the folder where you edit the code, and automatically synced to `main` before each run),
   and sets up a systemd user timer; runs missed while the machine was off are made up after boot. To remove it, use `scripts/install-updater.sh --uninstall`.

We do not recommend switching to GitHub self-hosted runners: on a **public** repo, a pull request submitted by anyone
can cause code to run on that machine, and GitHub itself advises against this. The approach above only needs that machine to push outward, and it accepts no inbound commands.

Notes on using GitHub Pages: on the free plan, Pages requires a public repo; Pages cannot set custom HTTP headers,
so of the headers recommended in the IIS section above, only those that the `<meta>` tags in `index.html` can express take effect (`frame-ancestors` does not);
Pages caches all files for a fixed period of about 10 minutes, so after a data update it can take up to 10 minutes for users to see it.

## Recommended production data integration

The current site's `POST /Home/GetHospitalData` API has the following limitations that make it unsuitable for direct calls from the front end:

- Each call returns only **20** facility records, so getting all of the roughly 4,660 records takes about **280** paginated calls;
- Each response is about 390 KB and **contains server-side rendered HTML** (not a clean data format), so fetching the full
  dataset transfers nearly **97 MB**;
- It requires the `X-Requested-With: XMLHttpRequest` header to be accepted;
- **CORS is not enabled**, so browsers cannot call it directly across origins.

**Recommended approach**: on the back end (the server hosting the current site, or an environment with access to the source database), create a **scheduled job**
that, every N minutes (for example 5–15 minutes, depending on how often the data changes), exports directly from the database and outputs a `hospitals.json` conforming to the
`docs/DATA_SCHEMA.md` format (about 1.9 MB after normalization, about 330 KB gzip-compressed; the English transliteration can reuse `scripts/romanize.mjs`),
and publishes it to a static file host or CDN.

Another viable option is for the current site's team to add a **JSON endpoint that returns the full dataset** (paginated or not), provided it enables
CORS or is deployed on the same domain; the effect is equivalent to the scheduled export above.

Whichever you choose, the front end only needs the single file `public/js/data-source.js` to change (replace `fetch('./data/hospitals.json')`
with a call to the new endpoint, and make sure the returned object still matches the `{ meta, vaccines, groups, hospitals }` structure);
no other code needs to change at all.

## Security

**Third-party libraries** (checked 2026-09-21): Leaflet 1.9.4 and leaflet.markercluster 1.5.3 are both the latest stable versions on npm
(Leaflet 2.0 is still in alpha, is pure ESM, removes the global `L`, and markercluster is not yet compatible, so upgrading is not recommended for now).
The files in `public/vendor/` are byte-for-byte identical to the npm packages; `npm run verify-vendor` verifies this with sha256, and `npm test` includes the check as well.
`npm audit` reports 0 issues. Leaflet has one advisory with no patched version yet, CVE-2025-69993 (`bindPopup()` renders the string passed to it as HTML,
which the maintainers consider documented existing behavior); this site **does not use** popups / tooltips, and all data strings are written via `textContent` or attributes, so it is not affected.

**Front-end protections**: the CSP in `index.html` disallows inline scripts and styles and opens up only images from the two basemap domains; Trusted Types is also enabled
(`public/js/trusted-types.js`), allowing only the fixed HTML strings of Leaflet and `map.js`. If you later change the pin HTML or the basemap
copyright string, you must update that file's allowlist at the same time, or the e2e tests will fail because of console errors. External links always use `rel="noopener noreferrer"`,
and booking URLs accept https only. The user's location exists only in memory and is never written to the URL, storage or any request (though when zoomed in on the map, the basemap server can infer the approximate area from tile requests).

**Data pipeline**: responses from the source website are always treated as untrusted. `scripts/sanitize.mjs` rebuilds every field to be published using an allowlist
(stripping control characters and bidirectional text control characters, limiting length, checking numeric and coordinate ranges, and validating phone and URL formats),
and both `normalize.mjs` and `keep-live-data.mjs` use it as the final gate; `harvest.mjs` sets limits on a single response, total transfer volume, records per page, and total record count.
The related tests are in `tests/security.test.mjs`.

**GitHub Actions**: each job uses least privilege (only deploy has `pages: write`, and no job can write to the repo),
all actions are pinned to full commit SHAs, `${{ }}` is always passed in through `env:` rather than written directly into commands, and checkout does not persist credentials.
When upgrading an action version, re-verify and update the SHA. We recommend going to the repo's Settings → Environments → github-pages and confirming that only the `main` branch is allowed to deploy.

**Limitations of GitHub Pages**: HTTP headers cannot be set, so there is no `frame-ancestors` / `X-Frame-Options` (which prevent embedding by other sites).
This site has no login state and no sensitive actions that could be induced by clicks, so the risk is low; if you switch to a host where headers can be set, please add them.

## Basemap

The basemap is chosen by UI language, so that place names are readable (for the evaluation process and measured evidence, see `docs/BASEMAP.md`):

- **Traditional Chinese**: the National Land Surveying and Mapping Center (NLSC) "NLSC map (通用版電子地圖)" `EMAP` (Chinese place names, loads faster for users in Taiwan); if it fails, it falls back to the official OpenStreetMap tiles.
- **Japanese**: same as Traditional Chinese (Japanese users can read kanji road names, and they match the street signs).
- **Other locales** (en, ko, id, vi, th, tl): NLSC "臺灣通用電子地圖EN" (the English edition of the NLSC map) `EMAP8` (English place names across Taiwan); if it fails, it falls back to OpenStreetMap and shows the notice "place names may be shown in Chinese". Currently no key-free source provides Korean street names, so ko also uses English.

**Users can switch by themselves**: the legend (bottom left on desktop, expanded by default; top right on mobile, collapsed by default) contains a "Basemap" radio group. In Chinese / Japanese UIs you can choose
"NLSC map (通用版電子地圖)" or "OpenStreetMap"; in foreign-language UIs you can choose "NLSC (English)", the Chinese edition of NLSC (place names match the street signs), or "OpenStreetMap".
The change takes effect immediately and the attribution bar changes with it; the choice is stored in the browser's localStorage under `vaxmap.basemap`, **with the Chinese-name and foreign-name categories stored separately**,
and each is applied when you switch locale. If the chosen basemap fails to load, it still automatically falls back to the next one and shows a notice, and the radio button also switches to the basemap actually displayed.

When the locale is switched the basemap changes immediately, without reloading the page. The order is determined by `BASEMAP_CHAINS` in `public/js/map.js` (the first entry in each chain is the default,
followed by fallbacks in order; layers on the same host are treated as failing together); the CSP `img-src` in `index.html` allows only these two domains (EMAP8 and EMAP share a host). For testing, you can add
`?tiles=nlsc` / `?tiles=osm` / `?tiles=nlscEn` to the URL to specify the starting basemap (it must be in the current locale's chain), add `?tiles=fail` to simulate failure of the default basemap,
or use a form such as `?tiles=fail:osm` to fail only the specified basemap.
**Before going live**, be sure to:

- Review the [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/). The official OSM tile servers
  are run on donations with no availability guarantee, and the policy explicitly states that heavy-traffic uses must not rely on them; violations may lead to a block without warning.
  This is fine for a prototype and low-traffic demos; if it will be the default basemap of a public production service, we recommend switching to self-hosted tiles or a commercial tile provider
  (MapTiler, Stadia, Mapbox, etc., most of which still draw their maps from OSM data). Currently the default for every locale is NLSC, and OSM is used only as a fallback or when the user chooses it;
- The NLSC's official description of its WMTS is that "users need not apply" to connect, but it has no published traffic limit or service level; the default basemap for every locale is on NLSC (EMAP / EMAP8),
  so before going live and before traffic grows, we recommend confirming with the National Land Surveying and Mapping Center in the name of Taiwan CDC (see `docs/BASEMAP.md`).

## Browser support

The site uses modern browser APIs (`fetch`, ES modules, CSS Grid, `<details>`, `prefers-color-scheme`),
targeting Chrome, Edge, Firefox and Safari (including iOS Safari) from the last two years. IE11 is not supported, and no polyfills have been added for it.

## Known limitations

- The data is a snapshot (updated twice a day), not live; always call the facility to confirm before going for a vaccination.
- Clinic hours are shown as morning / afternoon / evening bitmasks converted from National Health Insurance Administration data; they are only approximate time slots, not an exact clinic schedule.
- Facility names and addresses keep the source's original text (for example 「台北長庚紀念醫院」 is the official name); only the county/city and district fields are normalized to use 「臺」.
- English facility names are machine transliterations (personal names are joined in pinyin, and only about 25 well-known hospitals use their official English names) and are not official translations;
  English addresses are generated in Chunghwa Post format and keep only the first street number.
- The UI text for the six foreign languages (ja, ko, id, vi, th, tl) is an AI first draft and should be reviewed by native speakers before going public.
- State such as location and map extent is not written into the shareable URL (URL hash); only the filter conditions and the selected facility are shared.
- IE and older Android WebView have not been tested; map tiles may fail to load on unstable networks (there is automatic fallback and manual basemap switching).

## Differences from the current site

| Problem with the current site | This prototype's approach |
|---|---|
| You must close a blocking announcement pop-up before entering the site | The announcement becomes a dismissible header banner that does not block interaction |
| Data is requested in synchronous XHR batches of 20 records | Loads a single JSON at once (about 330 KB gzip, including the English transliteration), and the front end filters / sorts locally |
| Map pins show only "open / closed" | Pins use shape plus color to express three states at once: whether the clinic is open today and whether the selected item is in stock |
| There is no list; you can only click pins on the map | Provides a facility list sorted by distance, interacting in sync with the map |
| Filtering is a single-select pop-up | Filtering becomes multi-select chips (item, group, region, in-stock only, open today, etc.) |
| Stock shows only "yes / no" | Likewise shows only "in stock / out of stock" (raw quantities are not published, to keep the public from misreading what the numbers mean) |
| There is no navigation feature | The detail page provides a call link (`tel:`) and a Google Maps directions link |
| Filter state cannot be shared | Filter conditions and the selected facility are encoded into the URL (URL hash), so they can be shared directly, bookmarked, and restored with back / forward |
